# Research record: native-preserving AI session archives

**Evidence cut-off:** 2026-08-12
**Access date for web sources:** 2026-08-12 unless noted otherwise
**Scope:** nine named agent environments on five named hosts
**Privacy:** fleet probes inspected executable metadata, paths, aggregate counts, SQLite table/column names, and JSON key/type names only. No prompt, response, reasoning, tool output, credential, or transcript excerpt appears here.

## Executive findings

There is no present standard that can replace the nine native stores without loss. The surveyed formats address distinct purposes:

- Harbor ATIF v1.7 is a rich JSON **interchange** format.
- Letta trajectory v1 is a deliberately compact **agent-consumption** format.
- OpenTelemetry GenAI and OpenInference are **telemetry/observability** conventions.
- Agent Audit Trail is a privacy-preserving, tamper-evident **audit** proposal.
- SQLite FTS, AgentsView, Agent Sessions, cass, claude-vault, and ccusage provide useful **read/index/analysis** capabilities.

None is a byte-preserving archive format for all vendor data. The archive of record must therefore retain each collected native artifact unchanged, with a capture manifest beside it. Parsing, indexing, normalization, analytics, and export may be persisted for convenience only when marked non-authoritative and rebuildable from native artifacts and manifests.

The supplied `/Users/johnw/Desktop/session-files.md` reached the same broad native-first conclusion, but current evidence corrects material details: Codex 0.147 has trusted lifecycle hooks; Droid has `SessionEnd` hooks; Letta 0.2.5 covers all five target CLI families; OpenCode is currently WAL-mode SQLite; the installed Codex desktop bundle is `ChatGPT.app` with bundle identifier `com.openai.codex`; and the installed Droid desktop bundle is `Factory.app`. The supplied recommendation is evidence, not an architectural premise.

## Evidence notation and method

Material claims are labeled as follows:

- **P (primary):** vendor documentation, a published specification, authoritative source, or installed first-party documentation.
- **O (observation):** read-only local or SSH fleet evidence collected on 2026-08-12.
- **S (secondary):** community documentation or a tool's documented interpretation of another product's private format.
- **I (inference):** a conclusion drawn from P/O/S evidence.
- **U (unknown):** not established without guessing or inspecting content beyond the privacy boundary.

Confidence is **high**, **medium**, or **low**. A primary source may still leave an implementation detail unknown; an observed file can establish presence without establishing its semantic completeness.

All five hosts were reached read-only. `hera` was inspected locally; `clio`, `vps`, `vulcan`, and `andoria-08` were inspected over batch SSH. Files were not changed. The transient probe script was removed. Aggregate sizes are discovery estimates, not backup-capacity forecasts, and one macOS `stat` expression returned filesystem text rather than a newest-file epoch; no freshness claim relies on that field.

### Corrections to the supplied brief

1. **Codex hooks:** the assertion that Codex has no hooks is obsolete. Current [Codex hook documentation](https://learn.chatgpt.com/docs/hooks) lists `SessionEnd`, supplies `session_id` and `transcript_path`, and warns that transcript format is not a stable hook interface. Hooks can be disabled and `SessionEnd` has a short timeout. **P/high.**
2. **Letta coverage:** the announcement described fewer harnesses; repository release 0.2.5 now lists all five target CLI families among a broader adapter set. **P/high.**
3. **OpenCode:** current history is `~/.local/share/opencode/opencode.db`, with legacy JSON fallback. Fleet inspection found WAL mode and session/message/part-related tables. **O+S/high.**
4. **Desktop names:** `Codex.app` and `Droid.app` are conceptual surface names in this study. The installed bundles on both Macs are `ChatGPT.app` (`com.openai.codex`) and `Factory.app` (`com.electron.factory`). **O/high.**
5. **Canonical normalization:** the user's clarified requirement supersedes the brief's canonical-store language. Native bytes are authoritative; all normalized forms are optional derivatives. **Requirement, not an empirical claim.**
6. **Git/Parquet as archive:** a transformed Parquet or recompressed rendition cannot replace original bytes. Git may track small manifests, but the measured Codex stores make ordinary Git unsuitable for the native payload tier. **I/high.**

**Inference:** standardizing a query result is useful; standardizing the archive payload is destructive. The stable boundary is a source adapter that can discover and describe opaque native artifacts. Format-specific semantic interpretation belongs to versioned readers and can improve independently of collection.

### SQLite consistency is not byte identity

The [SQLite Online Backup API](https://sqlite.org/backup.html) says a completed destination is a bit-wise identical copy of the source **database image** at the snapshot instant; [`VACUUM INTO`](https://sqlite.org/lang_vacuum.html#vacuuminto) instead creates a vacuumed copy, and [`sqlite3_rsync`](https://sqlite.org/rsync.html) copies a live database over SSH. These methods can produce a consistent logical read snapshot, but they do not preserve the producer’s original artifact set—its exact main-file, WAL and SHM bytes, names and metadata—as native files. Two preservation needs must therefore remain distinct:

1. a **native forensic capture** of the exact source database/WAL/SHM generation, acquired as a coherent bundle under source-local coordination; and
2. a **logical read snapshot**, created by SQLite for safe indexing and export.

The former is authoritative native evidence; the latter is an optional, rebuildable capture aid unless the vendor itself defines it as an export. Copying a main database without its active WAL can omit committed transactions. Copying database, WAL and SHM at unrelated instants can produce an incoherent bundle. **P+I/high.**

| SQLite and FTS | [`sqlite-simple` 0.4.19.0](https://hackage.haskell.org/package/sqlite-simple) is stable mid-level access; [`direct-sqlite` 2.3.29](https://hackage.haskell.org/package/direct-sqlite) includes BLOB and FTS support; SQLite CLI remains reusable | standard `sqlite3`, mature backup API exposure and many ORMs | Both satisfy the small derived index; Python is somewhat easier for direct backup API use, but invoking vetted SQLite tools keeps that outside custom code |
| DuckDB/columnar analytics | [`duckdb-simple` 0.1.5.1](https://hackage.haskell.org/package/duckdb-simple), 362 recorded downloads, one reverse dependency, no Hackage build report; broad typed API but young | Official [DuckDB Python 1.5.5](https://duckdb.org/docs/stable/clients/python/overview), direct JSON/Parquet/Arrow/Pandas/Polars support | **Python materially stronger**, but DuckDB is optional and not justified for baseline lexical search |
| Filesystem notification | [`fsnotify` 0.4.4.0](https://hackage.haskell.org/package/fsnotify), cross-platform | third-party watchdog or platform APIs | Haskell adequate; notifications are latency hints, not correctness |
| SSH/rsync/subprocess | [`typed-process` 0.2.13.0](https://hackage.haskell.org/package/typed-process), binary streams, async/STM integration | standard `subprocess`, mature SSH libraries | Parity when reusing system SSH/rsync; no embedded SSH stack is needed |
| Concurrency and bounded retries | `async`, STM and lightweight threads | `asyncio`, threads/processes | Both adequate; Haskell has a strong fit for explicit state transitions and cancellation |
| CLI ergonomics | [`optparse-applicative` 0.19.0.0](https://hackage.haskell.org/package/optparse-applicative), generated help and shell completion | standard `argparse`; Typer/Click if desired | Parity; Haskell needs no CLI framework beyond one mature library |
| Hashing/integrity | [`crypton` 1.1.4](https://hackage.haskell.org/package/crypton) supports SHA-2/HMAC/signatures; or reuse platform digest tools | `hashlib`, `hmac`, `cryptography` for signatures | Python stdlib is easier for SHA-256/HMAC; Haskell library is current and adequate. Signatures are optional. |
| ATIF/OpenInference integrations | ATIF can be emitted as JSON; no listed OpenInference Haskell instrumentation | Harbor’s Pydantic reference and extensive OpenInference Python packages | Python materially stronger for optional live observability/export plugins, not native collection |
| Letta normalizer | Haskell would use the TypeScript CLI/runtime behind the generic plugin boundary | Official `agent-trajectory` Python wrapper embeds the generated JavaScript runtime and provides a direct Python import | Python has a convenience advantage for this optional normalizer, not native collection or authority |
| Testing schema drift and state machines | QuickCheck/Hedgehog/tasty/Hspec ecosystem; algebraic types make completeness states explicit | pytest/Hypothesis and rapid fixture authoring | Both strong; Haskell favors invariant-heavy core, Python favors adapter iteration speed |
| Nix packaging and fleet deployment | GHC/Cabal package can be pinned and distributed as one closure; compilation is heavier | Python closure is easy but dependency closure grows with analytics/observability packages | Haskell is practical if dependencies stay minimal; Python becomes easier if optional Python ecosystems are made core |

**Research conclusion (I/high):** Haskell is a sound practical choice for a small orchestration and SQLite-index core because the hard requirements are byte I/O, hashing, subprocess control, state transitions, JSON inspection, and SQLite—not machine learning or dataframe analytics. Python would reduce effort if the design made official DuckDB, Harbor Pydantic, OpenInference, or a rapidly changing Python parser ecosystem mandatory. The native-first design deliberately keeps those optional and executable-separated. A bounded build/packaging experiment remains appropriate before implementation, but current evidence does not justify overriding the user’s Haskell preference.

## Unknowns, evidence gaps, and research risks

1. **Claude standard-account Desktop:** third-party-mode storage is well documented, but exact completeness and retention of ordinary local, SSH, cloud, Dispatch, and side-chat surfaces are not. Side chats are documented as not saved. **U/high impact.**
2. **Codex Desktop:** no distinct authoritative local transcript root was established beyond shared Codex sessions/state and generic app-profile data. **U/high impact.**
3. **Cursor IDE:** Agent JSONL is readable, but DB-only chat blobs and cloud-only sessions are not generally decoded. Preserving bytes is possible; complete semantic search is not yet proved. **U/high impact.**
4. **Factory Desktop/cloud:** whether the selected organization exposes Sessions API access, its exact retention setting, and which app-only sessions lack local JSONL remain unknown. **U/medium-high.**
5. **Live SQLite exact-byte coherence:** a logical online backup is consistent, but it does not preserve the producer’s original main/WAL/SHM artifact bytes and metadata as a coherent native bundle. Such a bundle requires a stable source interval, filesystem snapshot, or coordinated quiescence. Feasibility and acceptable disruption must be measured per host before implementation. **U/high.**
6. **Native pruning:** Claude cleanup settings, desktop archive/delete behavior, and vendor migration can delete or rewrite history before a daily run. Scheduled cadence must be validated against actual churn. **Risk/high.**
7. **Identity collisions:** vendor session IDs are not globally unique across host, account, source kind, migration, or copied roots. No reader may use native session ID alone as archive identity. **Risk/high.**
8. **Scale:** aggregate roots include caches and sidecars, so observed KiB is an upper-bound discovery signal. Actual unique native bytes, daily change rate, and restic dedup ratio require a privacy-safe dry run. **U/medium.**
9. **Licensing:** cass’s rider requires legal/operational review before code reuse or deployment in contexts covered by it. **Risk/medium.**
10. **Future schema drift:** Codex record types, OpenCode migrations, and desktop stores are active implementation details. Adapter parsers must fail open for preservation and fail explicit for interpretation. **Risk/high.**

## Research conclusion

The evidence supports a native-first, reconciliation-based archive with optional derived readers. It does **not** support a normalized canonical store, hook-only collection, live file synchronization, one global native-session-ID namespace, or claiming complete desktop/cloud coverage where vendors do not document it. Existing tools substantially reduce transport, snapshot, backup, and search work, but a small archive coordinator is still needed to preserve provenance, byte identity, capture generations, explicit gaps, and rebuild boundaries across all five hosts. The architecture and reversal thresholds are specified in [DESIGN.md](DESIGN.md).
